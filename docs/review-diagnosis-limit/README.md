## 4. 「公開中の結果」と「途中回答」を分けた理由
現状は途中保存も確定も同じ行に書き、再編集を始めただけで公開結果が下書きに戻り上書きされます（実コード確認）。回数制限と両立しないため、途中回答は `salon_culture_drafts` に分けました。確定時に12問＋追加5問を1つの診断として公開します（既存の保存関数を内部で呼ぶだけで、軸の計算式は複製していません）。

## 5. アプリ切替〜0059適用までの旧経路の期間への対処
v1 草案では「0058適用→アプリ切替→0059」のあいだ旧RPCで制限を迂回できました。v2 では **制限を0058の表トリガーに移した** ため、0059を待たずに、0058適用の瞬間から旧RPC・直接API・service_roleの直接INSERTも同じ規則で制限されます。
- 0059は多重防御の整理（使われなくなった入口の権限を外す）で、制限の成立には不要です。
- 0058適用〜アプリ切替の間の旧アプリは、(a)新規の初回保存は従来どおり動く（トリガーが状態を作る）、(b)確定済みの人の再編集は拒否される（旧アプリはエラー表示になる）。この間は再編集ができません。
- 適用順: 0058適用 → アプリ切替（commit_diagnosis_result / confirm_salon_culture_diagnosis を使う）→ 0059適用。切替の間隔は短くしてください。

## 6. 本人用・店舗用の同期の確認結果（具体的な衝突）
実コード（0030の `save_salon_store_culture_profile`）は、**初期店舗**（salon_onboarding_assignments にある店舗）を保存すると、同じトランザクションで **オンボーディング本人の salon_culture_profiles を無条件にupsert**（回答・状態・8軸・AI要約を上書き）します。担当者が誰でも同期されます。
- 衝突: 本人が自分の結果を確定してロックしても、店舗の担当者が店舗結果を変えると、本人の確定結果が本人のロックを通らずに書き換わります。「本人・店舗を独立管理」と矛盾します（制限導入前から存在する挙動）。
- 草案の挙動: (1) 本人の行が確定済みなら同期はスキップ（本人の結果・ロック・回数に触れない）。(2) 本人の行が無い／未確定なら従来どおり書き込み（初期化）、その結果が確定なら本人用の「初回保存」として状態を作る（本人は導入後1回変更できる）。同期自体を無断で追加・削除はしていません。
- 副作用（要判断）: 本人の確定結果と、初期店舗の店舗結果が食い違うことがあります。読み取り側は、本人の行を読む画面（`app/salon/mypage`・`/salon/culture/*`）と、旧マッチング（0011）です。店舗側は店舗マッチング（0031）。食い違いを許容するか、同期を廃止して旧マッチングを店舗結果に切り替えるかは、プロダクト判断が必要です（本草案は変更しません）。
- **同期のスキップは整合の解決ではありません**（「上書きしない」だけ）。マイページ（自分用）と、美容師に見える表示・マッチング（店舗用）の読み分けは `own-vs-store-readers.md` に、現行コードから一覧にしました。美容師向けの表示と現行のマッチングはすべて店舗用、マイページだけが自分用です。旧マッチング（自分用を読む）は関数として残っていますが、現行の画面からは呼ばれていません。会社ページ→店舗ページの再構成・スタッフ経由の変更は、別の変更として扱います。

## 8. 実Authで未確認のこと（ローカル検証では確認できない）
- 実 Supabase（JWT/PostgREST経由）でのRPC呼び出し、`auth.uid()` の実挙動、service_role の権限が草案どおりになるか。
- 本番データでのバックフィル結果（件数・内訳）。導入前に件数を確認するSQLを別途用意できます。
- 新規登録判定: `signUp` の応答（identities・created_at・確認メール送信時刻・app_metadata）、`auth.admin.updateUserById` による app_metadata 更新、確認待ちアカウントへの再登録時の応答が、想定どおりか。**「作成時刻と確認メール送信時刻（確認不要では確認時刻）が0.5秒以内」は、実Authで未確認の暫定条件**です（モックは想定を再現したもので、実Authの仕様の証明ではありません）。
- 新規登録の応答が想定と違う場合の影響は、**別々に**評価します。(a) 誤取り込み防止: 条件を満たさなければ印を出さない（時刻が返らない・差が大きいときは取り込まない）ので、既存アカウントへの誤取り込みは起きにくい。ただし「起きない」とは断定できません（実Authで再登録の応答を確認するまで未確認）。(b) 正当な新規会員への引き継ぎ成功: 応答が想定と違うと**引き継ぎに失敗する側に倒れます**（結果が保存されない）。この場合は「期限切れ」ではなく「登録の状況を確認できなかったため保存できませんでした。もう一度診断を受けてください」と案内します。実Authで新規登録→確認メール→取り込みが成功するかは、実環境での確認が必要です。
- 同時要求（印の複数発行）: モックと純粋関数で、「最後に書かれた記録の印だけが有効」「Aが取り込み完了後にBの記録が更新されても初回結果は1件」を確認。実Authで updateUserById が同時に来たときの順序は未確認。

| 美容師: ロック中の再診断 | 保存されない（diagnosis_change_locked） | 「結果の保存に失敗しました。もう一度お試しください。」（次に変更できる日は出ない。何度押しても同じ） |
| 美容師: 前回と同じ回答の再保存 | 追加されない（回数も消費しない） | 保存に失敗したと表示される（旧アプリは追加された行を期待するため）。実害はなし |
| サロン: 初めての本人用・店舗用の診断（途中保存・確定） | 従来どおり。初回確定で状態が作られる | 変化なし |
| サロン: 確定済みの人が診断を開いて途中保存する | 保存されない（diagnosis_use_confirm） | 「保存に失敗しました。もう一度お試しください。」（旧アプリの途中保存は、確定済みの行を下書きに戻して上書きするため、止まる＝公開中の結果は守られる） |
| サロン: ロック中の確定、追加5問の回答変更 | 保存されない | 同上の汎用メッセージ |
| サロン: 店舗の閲覧専用スタッフの保存 | 保存されない（権限） | 同上 |
| 初期店舗の保存による本人用の同期 | 本人が確定済みなら同期をスキップ（店舗側は保存される） | 変化なし（本人の結果は店舗の変更で上書きされない。食い違いが残る） |

まとめ: **0058適用〜アプリ切替の間は、確定済みの人の再診断・再編集ができません**（初めての診断と通常の閲覧は従来どおり）。メッセージは汎用で、次に変更できる日は表示されません。切替を数時間以内に行えるよう、アプリを先に用意しておく必要があります。

## 10. 失敗時の復旧手順（巻き戻し→再開の手順は APPLY_PROCEDURE.md。再開SQLは 0058_resume.draft.sql）
`0058_rollback.draft.sql`（未適用の草案）で、制限だけを外して適用前の挙動に戻せます。状態表は消しません（回数の記録・途中回答を失わないため）。
1. 0059を適用済みなら、巻き戻しSQLのA（権限を戻す）が先に実行される（同じファイルの先頭）。
2. トリガー4つと新関数を削除（B・C）。旧RPC・直接INSERTは適用前と同じ挙動に戻る。
3. 美容師の新アプリは関数が無いDBでは従来の保存に戻るのでそのまま動く。サロンの新アプリ（下書き＋確定）は新関数が必要なので、巻き戻す場合はアプリも一つ前の版に戻す。
4. 再適用するときは、状態表が残っているのでそのまま使える（回数の記録は保たれる）。
ローカルでの確認: `rollback-verify.sh`（0058+0059適用→巻き戻し→直接INSERTが通る・関数とトリガーが残らない・状態表が残る・旧サロンRPCの権限が戻る）。本番での巻き戻しは未実施・未確認です。
