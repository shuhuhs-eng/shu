# 0078（草案・未適用）8タイプ判定の同点順序の明示

本番への適用・push は保留。ここにあるのは草案・検証・手順のみ。適用済みのSQL（0004 ほか）は編集していない。番号の 0078 は仮（適用が決まってから確定）。

## 何を変えるか
`save_core_type_result(uuid)` の並べ替えだけ。**得点の降順 → 同点なら `CORE_TYPE_CODES` の定義順**（shimei_jishaku, aisare_ace, niaiwase_master, trend_maker, iyashi_charisma, repeat_king, mirai_no_ace, brand_builder）。1位・2位に同じ規則。乱数・時刻・ユーザーIDによる加点で同点を隠さない。
変えないもの: 重み、得点の丸め（`round(,1)`）、履歴・初回確定への保存方法、引数・戻り値・権限、**保存済みの行（履歴・初回確定タイプ）**。新しい規則は、適用後に新しく保存される結果にだけ効く。

## なぜ必要か（実測）
旧(0004)は `order by value desc` だけで、同点の順序が未指定（ローカルのPostgreSQL 16では jsonb のキー順に従った）。アプリの定義順と食い違う。
- 合成ケース29,636件: 旧DBはアプリと3,285件で1位または2位が食い違い、新DBは0件。
- 例: 全軸50点 → 旧DB `aisare_ace`、アプリ `shimei_jishaku`。
- 経験者の実際の質問から作った回答（300,000通り）では、保存される1位・2位が変わるのは1.78%（1位が変わる 0.62%、2位だけ 1.16%）。詳しくは `impact_experienced.md`。

## ローカル検証（実施済み・本番には接続していない）
`bash docs/core-type-tiebreak-db/run_0078_verify.sh`（使い捨てDB `vfy_*` を作って消す。適用順は本番の現状 0058→0070→0059→0071→0072→0073→0074→0076→0077 のあとに 0078）。
- DB側 25項目すべて PASS（2回実行: 合成ケースと実回答）: 適用前チェックPASS／適用後チェックは適用前ならFAIL（検出力）／適用／適用後チェックPASS／適用前チェックは適用後ならFAIL（二重適用検出）／**履歴・初回確定タイプのハッシュが適用前後で同一**（適用前のハッシュを保持して適用後と比較する。旧版は左右が同じSQL結果で常にPASSしていた不備を修正。履歴を意図的に変えると FAIL になることを `VFY_INJECT_HISTORY_CHANGE` で確認済み）／二重適用は拒否／保存済み診断の再保存は冪等／巻き戻しで0004の定義・権限に戻る（履歴は残る）／二重の巻き戻しは拒否／再適用できる／想定外の関数定義には適用も巻き戻しも拒否。
- アプリ(TS)との突き合わせ: 新DBは合成29,636件・実回答70,810件で、1位・2位・差・8タイプの得点がすべて一致（0件）。旧DBは合成で3,285件食い違い。
- 自動テスト `tests/core-type-parity.test.ts`: DB（0078適用後）の結果を固定データにして、アプリの出力と一致を確認（5,311行）。
- **未確認**: 実際のSupabase上での実行（権限の付き方・既存の関数定義が本番でも0004と一致しているか）。適用前チェックがそれを検出する。

## 本番適用の手順案（運営者が実施。保留中）
1. 本番で `0078_preapply_check.sql` を実行（読み取り専用）。総合 PASS でなければ中止（関数の定義が想定と違う可能性）。
2. `0078_core_type_tiebreak.draft.sql` を実行（ガードが想定外の定義を検出すると何もせず中止）。
3. `0078_postapply_check.sql` を実行。総合 PASS であること。履歴・初回確定のINFO行（件数・ハッシュ）が手順1の値と一致すること。
4. アプリを配備（丸めの一致修正を含む版）。順序はどちらが先でも壊れない（DBが先なら保存が定義順になり、アプリが先ならプレビューだけ整数計算になる。両方そろうと完全に一致）。
5. 戻す必要が出たら `0078_rollback.draft.sql`（0004の定義に戻す。履歴は変更しない）。

## 注意
- 適用後に保存された履歴は、巻き戻しても残る（0004の規則では履歴は追記のみ）。
- 同点・丸め境界での1位・2位は、もともと僅差であり、定義順は優劣の根拠ではない。画面で「僅差」と表示する場合も、確信度ではなく暫定の表示（設計メモの 2.0 は暫定案）。
