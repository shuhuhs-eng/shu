# 0072 レビュー資料（草案・未適用）: 「大切にしたいこと」だけを更新する専用の保存関数

作成: 2026-11-15。**本番へは適用しない（レビュー後に別途判断）。SQLはコミット・pushもしていません（承認後）。** 適用済みの0058・0059・0070・0071は編集も再適用もしません。

## 1. なぜ必要か
診断結果から「サロン選びで大切にしたいこと」（`stylist_profiles.value_priorities`）を反映するとき、既存の保存関数（`save_stylist_profile` / `_v2`）はプロフィール**全項目**を引数に取ります。画面が読み取った値で全項目を書き戻すため、**別画面で同時に行った公開範囲・自己紹介などの変更を古い値で上書きしうる**競合がありました。
→ 対応: (1) アプリの反映の保存を一時停止（済み・下記）、(2) この1列だけを更新する専用関数を作る（本草案）。

## 2. 内容（`0072_value_priorities_save.draft.sql`・関数1つの追加のみ）
`public.set_stylist_value_priorities(p_value_priorities text[]) returns void`（SECURITY DEFINER・search_path固定）
- **引数は value_priorities のみ。** 公開範囲・生年月日・表示方法・その他のプロフィール項目は、引数で受け取らず、更新もしない（`UPDATE … SET value_priorities = … WHERE user_id = auth.uid()` の1文のみ）。
- **本人確認:** `auth.uid()` が無ければ拒否。更新するのは自分の行だけ（他人の行は指定できない）。
- **DB側の検証:** 1次元／ちょうど3件／NULL要素なし／重複なし／許可された12項目のみ（アプリの `VALUE_PRIORITY_OPTIONS` と同じ。テストで一致を確認）。
- プロフィールが未保存なら**行を作らず**拒否（`profile_not_found`）。
- 0070の before-update トリガー（生年月日・表示方法が未登録なら拒否）は、このUPDATEにも効く（既存の保存と同じ規則）。
- `profile_version` は進めない（1項目の更新で、`profiles` を触らず、保存関数との行ロックの競合を増やさない）。
- 前提: 0070適用済み。0071の適用状態に依存しない。既存の表・関数の定義は変更しない。

## 3. 権限
`revoke all … from public, anon, authenticated, service_role` のあと `grant execute … to authenticated` のみ。表の権限は付与しない（`authenticated` は `stylist_profiles` を直接書けないまま）。

## 5. 検証（ローカル・使い捨てDB。`0072_verify.sh`・**31件PASS／失敗0**）
- 適用前チェック総合PASS → 適用 → 適用後チェック総合PASS（FAILの行なし）。二重適用は拒否。
- 権限: authenticated のみ実行可（anon・service_role・PUBLICは不可）。表への直接UPDATEは不可。
- 正常: 3つが選んだ順に更新され、**value_priorities 以外の全項目（公開範囲・自己紹介・生年月日・表示方法・氏名・画像・受信設定）は不変**。他人の行も不変。
- DB側の検証: 2件／4件／重複／許可外／NULL要素／2次元配列／空／NULL をすべて拒否し、保存済みの内容は変わらない。
- 本人確認: 未認証は拒否。プロフィール未保存は拒否し行を作らない。生年月日・表示方法が未登録は、既存の規則どおり拒否。
- **競合（別画面のプロフィール保存と重なる）**: 実際に別接続でロック待ちを発生させて確認。
  - 5a プロフィール保存（公開範囲PUBLIC・自己紹介を更新）が先 → 専用関数は待つ → **公開範囲・自己紹介の変更が残り、value_priorities は専用関数の値**。

## 6. 残る制約（既存の仕様・0072では変えない）
- 5b の場合、`value_priorities` は後から確定した**プロフィール保存の入力値**になる（プロフィール保存は全項目を送る既存の仕様。古い画面から保存すると、その画面にあった値が残る）。専用関数の更新が、同時に行われた古い画面の保存で巻き戻る可能性はある（ごく短い間）。
- DBは重複を既存の保存関数では拒否しない（新しい専用関数は拒否する）。
