# 年齢の扱い（確定方針）— 0070 / 0071 / アプリの仕様と実装

状態: **確定方針に合わせて実装済み（未適用の草案・ローカル検証済み）**。本番適用・pushは未実施。以前の「生年月日未登録の既存会員は従来どおり表示」「年齢未登録の全員を保留にするか判断待ち」は**撤回**し、下記に置き換えた。

## 1. 仕様（確定）
| 項目 | 内容 |
|---|---|
| 生年月日 | **必須登録**。日本時間(JST)の今日を基準に満年齢を自動計算。生年月日そのものはサロンに出さない（どの経路でも返さない）。保存できる範囲は満15〜100歳（変更なし） |
| 既存会員 | 生年月日は推測して埋めない（年代 age_band からも作らない）。未登録でもログインできる。マイページ・プロフィールで入力を案内。**登録（生年月日＋表示方法の選択）が済むまで、サロン向け候補一覧・プロフィール画像・スカウト送信先から保留** |
| 保存 | プロフィールの新規保存・更新は、生年月日が未登録だと拒否（DBのトリガー `birth_date_required`）。登録済みの生年月日をNULLへ戻すことはできない（トリガー） |
| 表示方法 | 本人が選ぶ。**実年齢**（例 45歳）／**年代**（例 40代）。初回の選択は本人に求め、既存会員を勝手に実年齢にしない（未選択のあいだは保留）。切替は何度でも可。NULLへは戻せない |
| データの制御 | サロンへ返す年齢情報は、DBの関数で制御（画面で隠すだけではない）。年代表示で未承認の相手には、`age` のキー自体と生年月日がレスポンスに含まれない |
| 開示依頼 | 年代表示の美容師に対し、サロンは任意で「実年齢の開示を依頼」できる。興味あり・スカウトでは自動で開示しない。美容師は依頼元の店舗を確認して承認・辞退。未回答・辞退は年代のまま。承認は**依頼元の店舗にだけ**現在の満年齢（誕生日のあとも最新）。他の店舗へは流用しない。生年月日は承認後も出さない |
| 公開判定 | 表示方法とは**別の判定**: `stylist_salon_publishable` ＝ 生年月日が登録済み かつ 表示方法が選択済み かつ（満18歳以上 または 未成年フラグ解除）。判定は**正確な満年齢**で行い、年代表示でも未成年の保留は回避できない。承認しても非公開設定・未成年の保留は解除されない |
| 通知 | 既存のアプリ内通知を利用（依頼→美容師 `age_disclosure_requested`、承認→依頼したサロン `age_disclosure_approved`）。メール等の外部送信は追加していない |

## 2. 「依頼元サロン」の単位と権限（既存の店舗・会社・権限設計から決定）
- **単位 = 店舗（`salon_stores.id`）**。既存のスカウト・給与オファー・採用進捗がすべて店舗単位のため。会社所属だけを理由に別店舗へ開示しない（同じ会社の別店舗にも流用されない）。
- **依頼できる人** = その店舗で `can_manage_store_hiring` を満たす人（会社の company_owner / company_admin / recruiting_admin、担当店舗の area_manager、その店舗の store_manager / recruiter）。閲覧専用（viewer）は不可。ほかの店舗の担当者・他社は不可。
- **承認後に年齢を見られる人** = その店舗にアクセスできる人（`is_store_accessible`。閲覧専用を含む）。他店舗・他社は見られない。
- 依頼の対象: その店舗の候補（公開中・スカウト受信可・公開可）、またはその店舗へ「興味あり」を送った美容師（受信拒否・非公開でも、本人が送った相手には依頼可）。
- 同じ店舗×美容師の依頼は1件（連打・複数画面でも1件。DBの一意制約）。辞退した相手への再依頼はできない。

## 4. 運用上の影響（適用前に必ず確認）
- **0070の適用直後、現在公開中の美容師は全員、登録が済むまでサロン向けの一覧・画像・スカウト送信先から外れる**（本番の適用前チェック 行17 で人数を確認できる）。本人が生年月日と表示方法を登録すると、その場で再び表示される。
- **配備の順序: ①新アプリ → ②0070 → ③適用後チェック**。新アプリは0070が未適用でも動く（入力欄は出ず、候補一覧は従来の取得へ戻る）。旧アプリのまま0070を先に適用すると、既存会員がプロフィールを保存できなくなる（旧アプリは生年月日を保存より後に送るため）。
- 保留中の美容師へスカウトを送る経路は、DBで拒否される（旧画面・直接呼び出しも含む）。→ **要確認事項**（下記）。

## 5. 要確認（設計判断として置いた点。変更可）
1. 公開保留の美容師へのスカウトを、DBのトリガーで拒否する（保留の実効性のため）。不要なら `trg_scouts_publishable_guard` を外す。
2. 辞退した相手への再依頼は不可（状態は declined のまま）。再依頼を許すなら、期間を空けるなどの条件が必要。
3. 辞退の状態をサロンにそのまま表示する（「辞退されました」）。表示を「未回答」に寄せる案もある。
4. 承認の取り消し（撤回）機能はない。必要なら別途設計。
5. 美容師が年代→実年齢へ切り替えると、承認の有無にかかわらず全サロンに実年齢が出る（本人の選択）。
6. 承認は店舗単位。会社単位で一括承認する案は、承認範囲を広げるため採用していない。

## 追補（レビュー指摘2点の修正・本番未適用）
1. **一括保存**: アプリの保存は `save_stylist_profile_v2`（0070草案 1c-2）の**1回のRPC＝1つのDBトランザクション**。生年月日・表示方法・プロフィール（公開設定を含む）は、途中で失敗するとすべて取り消される。内部で既存の `set_stylist_birth_date` / `set_stylist_age_display_mode` / `save_stylist_profile` を呼ぶ（本人判定 auth.uid() はそのまま）。以前の「生年月日→表示方法→プロフィール」の3回呼び出しは廃止（例: 年代・公開→実年齢・非公開の保存が途中で失敗しても、実年齢表示だけが公開のまま残ることはない）。
2. **表示方法の未選択をDBでも拒否**: v2 は生年月日・表示方法（exact/decade）のどちらかが空・不正なら保存しない。さらにプロフィール行（stylist_profiles）のトリガーが「生年月日の未登録」に加えて「表示方法の未選択」も拒否するため、旧 `save_stylist_profile` を直接呼んでも未選択のまま保存できない。**DB対応の判定はサーバー側**（アプリがDBの `stylist_private.age_display_mode` 列を読んで判断。列が無い=0070未適用なら従来の保存関数。読み取りエラーなら保存しない）。フォームの項目欠落（未選択のラジオは送信されない）では判断しない。
3. 影響: 0070適用後、表示方法が未選択の既存会員は、プロフィール更新（0071の career_phase 更新を含む）時に表示方法の選択が必要になる（従来から生年月日が必要。公開されない扱いも変更なし）。
