# 運営管理画面：既存機能の調査と設計（ローカル・未実装・未適用）

ブランチ: `local/admin-console`（push済みの ad34d67 から分岐。再診断制限の 0058/0059 は含まない）。
本書は「調査結果」「設計」「外部設定」「レビューが必要なDB差分の方針」までです。**SQL適用・本番のアカウント発行・メール送信・請求/決済の実行は行っていません。**

## 1. 既存機能の調査結果（再利用できるもの）

| 領域 | 既存 | 使い方 |

## 2. 既存に無いもの（新規が必要）
- **メール送信基盤が存在しない**（resend/SMTP等の利用なし）。連絡通知・招待メールは外部設定が必要（9章）。
- 連絡スレッド（運営→相手、相手の返信、対応状況、内部メモ、メール送信結果）。
- 見学の受付〜実施確認〜請求の案件管理、新料金区分（登録手数料・見学料・採用料の2種）。
- サロンのアカウント招待（招待状態・再送履歴）。
- 会社所在地・地域ブロックの対応表（現在の所在地は店舗の `prefecture`/`city` のみ。会社本体に所在地は無い→「未設定」表示）。
- 運営によるプロフィール修正の変更履歴（変更者・日時・内容）と、影響の大きい変更の確認画面。

## 3. 画面構成
`/admin` ホーム＝件数のみ（未対応・返信待ち・見学予定・請求確認待ち）。件数→該当一覧→行から詳細。
メニュー: ホーム／会社・店舗／美容師／見学・採用案件／連絡・返信／請求・支払い（既存の契約・規約・整合性・実績資料・発行事業者は「その他」に格納）。
- 会社・店舗: 検索（会社名・店舗名・担当者名・登録メール）、絞り込み（47都道府県、地域ブロック、公開状態、担当者、対応状況）。地域ブロックは 北海道／東北／関東／中部／近畿／中国／四国／九州・沖縄 の**対応表を定数で持つ**（47県を漏れなく検証するテストを付ける）。所在地が無い会社/店舗は「未設定」。店舗エリア検索では該当店舗を行内に明示。会社詳細から 店舗・担当者・案件・連絡・請求へ。
- 美容師: 居住(`prefecture`)と勤務希望(`desired_work_location`)を別列・別検索。診断結果は**閲覧のみ**（運営が書き換える機能は作らない）。非公開情報・証明資料は、サロン側の画面・連絡本文へ自動転記しない（連絡の本文は運営が手で書く）。
- 変更履歴: 新表 `admin_audit_events`（変更者・日時・対象・変更前後）。公開状態・利用停止は確認画面を挟む。会社情報／店舗情報／公開設定は別フォーム・別履歴種別にし、診断回答・結果は編集対象にしない。

## 4. 管理者の入口と権限
- `/salon/login` の成功後、`is_platform_admin()` が true なら `/admin` へ（サロン名入力・店舗登録は求めない）。判定は `determineRoleEntryPath` の前、サーバー側のRPCのみ。メール文字列は見ない。
- `/admin/**` の各ページ・Server Action・Route Handlerは自分で `is_platform_admin()` を確認（既存方針）。新設する管理用RPCはすべて SECURITY DEFINER＋内部で同確認＋anon/public不可。一般サロン・美容師のURL直打ち／API直叩きを拒否するテストを付ける。
- 管理者が他者としてログインする機能（なりすまし）は作らない。

## 5. 連絡（運営→相手→返信）
新表（案）: `admin_threads`（相手種別 salon/stylist、相手user、対象会社・店舗、関連案件、状態: 未対応/相手の返信待ち/運営の返信待ち/完了）、`admin_messages`（`visibility` = `public_to_recipient` | `internal_note`、投稿者、本文）、`admin_message_notifications`（メール送信の成否・失敗理由・再送）。
- 相手に見せる本文と内部メモは**別列ではなく別visibilityの行**にし、相手側のRLS/RPCは `public_to_recipient` だけを返す。電話/メール対応の記録は内部履歴として追加。
- サロン宛て・美容師宛てはスレッドを分離。相手が美容師の場合、サロン側のどの画面にも出さない（本人の同意なく双方の返信・連絡先を共有しない）。
- どの入口（会社・店舗・案件）からも同じスレッドIDを開く。メール通知は「新着あり・ログインして確認」程度で本文を載せない。メール失敗でもスレッドは残り、運営一覧に「通知失敗」を表示。
- 閲覧・返信できる人（既存権限から）: サロン宛て=対象会社の company_owner / company_admin / recruiting_admin と、対象店舗の store_manager / recruiter。viewer と area_manager（担当店舗外）は不可（返信は書き込みのため `can_edit` 系に合わせる）。→ 対応表は実装時にテスト化。

## 6. 見学・採用案件
`stylist_salon_interests` を受け皿に、運営受付の案件表 `admin_visit_cases`（案）を新設: 受付→内容確認→サロンへ連絡→日程→実施確認→双方の意向→採用判断→請求。会社画面には「〇〇店への見学希望」を表示。運営確認前はサロンが請求・決済へ進めない（請求は運営が確定した行にのみ決済ボタン。既存の「確定→支払い」の流れと同じ）。

## 7. 請求・決済（新料金区分）
税抜: 登録手数料（1〜3店1万／4〜6店2万／7〜9店3万／10〜12店4万／13店以上は個別見積）、月額 当面無料、見学料 実施1回5万（採用有無に関わらず）、採用料 スタイリスト55万・アシスタント45万（見学料と相殺しない）。
- 請求は会社宛て、行（明細）に対象店舗・案件・料金区分・税抜・税・合計。状態: 下書き→運営最終確認→請求確定→支払い待ち→支払い完了（失敗・取消・返金は別状態）。**請求作成だけでは課金しない**。
- 重複防止: 「案件×料金区分」に一意制約（取消後の再請求は別途規則が決まるまで運営の個別確認）。決済通知は既存の `stripe_event_id unique` を再利用。13店舗以上は金額NULLのまま決済開始を拒否（DB側で検査）。カード情報は保存しない（Stripe Checkout、既存どおり）。
- 既存の `hiring_success_fees`（採用の成功報酬）との関係は**要確認**: 採用料55万/45万を既存表に載せ替えるか、新請求表に統合するかをレビューで決める。既存のStripe連携を壊さないよう、まず「新表を足して既存は触らない」案を推奨。
- **料金が未確定のケース（個別確認で止める一覧）**: 見学の取消・再見学の扱い／内定取消後の返金／登録後の店舗追加（段階料金の差額）／13店舗以上／見学料と採用料の同月請求時の請求書まとめ方／アシスタント・スタイリストの区別が不明な採用／既存契約会社への新料金の適用開始時期。

## 8. サロンアカウント発行
受付済み会社のみ対象。会社の新規作成と既存会社への担当者追加は別ボタン・別確認。パスワードは運営が決めず、受取人がメールのリンクから設定（Supabaseの招待メールを使用。**SMTP等の外部設定が必要**）。既存メールがある場合は所属を上書きせず「既存アカウントあり」として運営に止める。招待状態（招待中／利用開始／期限切れ／停止）と再送履歴、作成者・権限付与者を `admin_audit_events` に記録。本番でのアカウント発行・メール送信は本実装の検証では行わず、ローカル/テスト用モックとテスト用プロジェクトで検証する。
一般向け「サロン登録」は、会社名・担当者名・電話・メールの問い合わせ受付に変更。送信先メールは未確定（環境変数 `INQUIRY_TO_EMAIL` を空で置き、未設定なら受付内容をDBに保存するだけ。推測値は入れない）。

## 9. 外部設定（運営が用意するもの。未設定のまま進める）
1. メール送信（SMTPまたは送信サービス）と送信元ドメイン認証。2. Supabase Auth の招待メール文面・リダイレクトURL。3. 問い合わせ受付の送信先メール（未確定）。4. 運営者 `admin@beautyreach.jp` の platform_admins 登録（本番で人が実施）。5. Stripe: 新料金区分の商品/税設定（既存の設定を確認のうえ）。

## 11. 実装の順序と検証
1) 入口と権限・ナビ → 2) 会社/店舗/美容師の一覧（読み取り中心。DB変更なし）→ 3) 連絡 → 4) 案件 → 5) 請求 → 6) 招待・問い合わせ。1〜2はDB変更なしで実装可。3以降はSQL草案レビュー後。
検証: 他社/他店舗の拒否、連絡先の取り違え防止、内部メモ非公開、招待の重複、二重請求防止、スマホ表示（320/375px）。
