# 0062〜0064 のアプリ側実装：範囲と順番（案・未着手）

前提: 0062〜0064はDB適用済み（`0062_0064_APPLIED_RECORD.md`）。アプリはまだ呼んでいない。料金方式の切替・実請求・課金・メール送信は、この計画のどの段階でも「承認を得るまで実行しない」。
**Stripe連携は未完成**（請求用の決済受付の記録のみ）。税10%・切り捨ては草案で、税務上の適用確認は未済。

## 調べて分かったこと（実装の前提）
1. **運営が見積・請求・請求行を読む手段が、いまのDBに無い。** 0062の6表は誰にも直接の権限が無く（意図的）、読み取りの関数は会社側の `company_list_quotes`・`billing_list_invoices`（確定済みのみ）だけ。運営の画面は、読み取り専用の関数を足さないと作れない → **新しいマイグレーション（0065・読み取り専用）が必要**（承認が必要）。
2. **請求用のStripe決済は、既存のStripe実装と別物。** 既存の `lib/stripe/*` は月額・旧成功報酬・スカウトクレジット用（`stripe_checkout_records`）。新しい請求は `admin_invoice_checkouts` を使うが、Stripeセッション作成・通知反映・`needs_review` の解消の関数がまだ無い → **書き込み側のマイグレーション（0066）とwebhookの分岐が必要**。
3. 会社側は、見積の確認・同意（`company_list_quotes` / `company_respond_quote`）と、確定済み請求の表示（`billing_list_invoices`）がそのまま使える。
4. 会社所在地（0063）と料金方式の状況（0064 `admin_billing_regime_status`）は、運営用の関数が既にある。

## アプリ側で守ること
- 権限は常にDB関数に任せる（画面の出し分けだけで制御しない）。運営は `is_platform_admin()` の確認を通す。
- 決済額・請求額はDBから取り、クライアントの値を信用しない。
- 書き込み操作は、再送しても重複しないDBの仕組み（`request_id`、同じ結果を返す関数）を前提に、ボタンの二重押下・通信切れ後の再試行を画面側でも抑止する。
- DBの拒否メッセージ（例: `checkout needs review`、`case has an invoiced fee; …`、`hire without a confirmed visit needs individual review`）は、日本語の案内に対応づける（内部の英語メッセージをそのまま見せない）。
- 運営専用の内部メモは会社に見せない。採用料は「運営の双方確認＋サロンの内定意思確認」後。見学未実施の採用は個別確認に回す。
