# 既存契約と新料金の移行・旧請求の抑止（確定方針を反映 v2・未適用）

0060（一覧・検索）とは**別のレビュー**です。対応するSQL草案は 0064（請求方式の切替と旧請求の抑止）、0062（新しい請求）です。**本番には何も適用していません。**

## 1. 確定した方針
- 旧→新の料金は**会社ごとに明示的に切り替える**。
- **却下**: 「旧の成功報酬を作り続け、運営が毎回免除する」運用。
- 新方式の案件では、旧の成功報酬の**自動作成をシステムで止める**。旧の画面・APIから旧請求を確定・支払いできないようにする。
- 重複検出SQLは**補助的な監査**。主な防止はDB側。
- 既存の有効な請求・支払いは**削除も再計算もしない**。
- 進行中の案件を旧／新のどちらにするか、具体的な基準を持つ。
- 月額を無料にする会社に旧サブスクが残る場合は、**確認→停止→反映確認**を切替手順に入れる。実際の解約・課金操作はまだ行わない。

## 2. 既存の仕組み（関数は書き換えない）
| 既存 | 本計画での扱い |
|---|---|
| `hiring_success_fees`（pending_confirmation→confirmed→invoiced→paid/waived/cancelled） | 行は削除・再計算しない。**挿入前・更新前のトリガーを足して**新方式の案件の作成・確定を止める（既存の関数・トリガーは変更しない） |
| `hiring_create_success_fee()`（採用成立で旧の行を自動作成、`on conflict do nothing`） | 書き換えない。新方式の案件では、挿入前トリガーが行の作成を**黙ってスキップ**（採用成立の処理自体は失敗させない） |
| `begin_success_fee_card_checkout`・`stripe_checkout_records` | 書き換えない。挿入前トリガーで、新方式の案件の旧成功報酬のカード決済と、新方式の会社の旧月額サブスクの決済開始を拒否 |
| `organization_subscriptions`（月額・Stripe） | 自動解約しない。切替の手順で確認（後述） |
| `organization_contract_settings` | 変更しない（旧方式の根拠として残す） |

## 3. 方式の決め方（0064）
- `organization_billing_regime`（会社ごとに1行、`new` へ**一方向**。`effective_from` を持つ）と、`hiring_process_billing_basis`（案件ごとの明示指定）。追記専用で、更新・削除不可。
- 案件の方式 `_hiring_process_basis(process)` の決定順:
  1. 案件に明示指定があれば、それ。
  2. 会社が新方式で、**案件の作成日時 ≥ 会社の `effective_from`** なら **new**。
  3. それ以外は **legacy**。
- 切替 `admin_set_billing_regime(会社, effective_from)`: 運営者のみ。`effective_from` は過去にできない。会社単位で、繰り返しはエラー。

## 4. 進行中の案件の具体的な基準
| 状態（切替の時点） | 方式 | 理由・操作 |
|---|---|---|
| 切替前に作成された案件で、旧の成功報酬の行が `confirmed` / `invoiced` / `paid` | **legacy のまま** | 既存の請求・支払いは変更しない。旧の画面で完結させる |
| 切替前に作成された案件で、旧の行が `pending_confirmation` | legacy（既定）。**新にしたい場合のみ**、運営が `admin_set_process_billing_basis(案件, 'new', 理由)` で個別に指定 | 旧の行は**削除せず `cancelled` にして履歴を残す**（イベント記録）。確定以降の進んだ行は拒否 |
| 切替前に作成された案件で、旧の行がまだ無い（採用前） | legacy（既定）。新にしたい場合は上と同じ個別指定 | 採用成立の時に旧の行が作られるため、新にするなら成立前に指定する |
| 切替後に作成された案件 | **new** | 旧の行は作られない（トリガー）。採用料・見学料は新方式の請求で扱う |
| 見学（新しい概念） | new のみ | 旧には存在しない |
- 「新にする」個別指定は、会社が新方式であることが条件。条件を満たさない指定、進んだ旧請求がある案件への指定は拒否される。

## 5. 旧請求の抑止（DBで強制）
| 対象 | 動作（0064のトリガー） | 検証 |
|---|---|---|
| 新方式の案件で採用成立 → 旧の行の自動作成 | 挿入前トリガーがスキップ（行は作られない） | N系（新方式の案件に旧行が作られない） |
| 新方式の案件の旧行を confirmed / invoiced / paid にする | 更新前トリガーが拒否（旧画面・旧APIからでも） | G1・G2 |
| 旧成功報酬のカード決済の開始（新方式の案件） | `stripe_checkout_records` の挿入前トリガーが拒否 | G3 |
| 旧の月額サブスクの決済開始（新方式の会社） | 同上で拒否 | G4 |
| 取消（cancelled）・旧方式の会社の従来操作・カード登録など無関係な決済 | 止めない | G5・G6・G7 |
| 旧の画面・APIからの操作 | 上記トリガーで失敗する。アプリは分かる日本語に変換（`lib/billing/actions.ts` への追加を想定。未実施） | — |
- 既存の請求行（切替前の有効な行）は、トリガーの対象外（legacy の案件）。検証で行数・内容が不変であることを確認（H1〜H2）。
- 整合性チェック `get_admin_billing_integrity_issues` は、新方式の案件を「成功報酬の欠落」として誤検知しないよう、判定を1つ足した版に置き換える（巻き戻しSQLは0040の元の関数）。

## 6. 月額無料と旧サブスクの手順（切替手順に組み込む）
切替 `admin_set_billing_regime` は、次の場合に**実行できない**:
- 有効なサブスクがあり、かつ `cancel_at_period_end` が false（停止の予約が反映されていない）。
- 未完了のチェックアウト（pending/open）がある。

運営の手順: ①旧サブスクの有無を確認 → ②（会社と合意のうえ）Stripe側で期間末に停止を予約 → ③**アプリのDBに停止の予約が反映されたことを確認**（`admin_billing_regime_status` の `switch_blocked_reason` が空）→ ④切替を実行。**②の実際の解約操作は、この作業では行っていない。**

## 7. 重複リスクの検出SQL（補助）
`billing_overlap_check.sql`（読み取り専用）: 新方式の会社で旧成功報酬が未完結のもの／同じ採用に新旧両方の行があるもの／旧サブスクが有効なまま新方式の会社。運営画面の整合性チェックへの接続は未実装。**防止の本体は4〜5のDB制約で、これは抜けの監査用。**

## 8. 未確定で、個別確認で止めるもの（勝手に規則を決めない）
見学の取消・再見学／内定取消後の返金／登録後の店舗追加（段階料金の差額）／既存契約会社への登録手数料の請求有無・時期。13店舗以上は、スタッフが金額を提案し会社が合意した後に請求対象になる（0062に見積合意の項目を追加予定。未作成）。
