# 既存契約と新料金の移行対象・二重請求防止（案・未適用）

**この文書は案です。** 既存の請求を削除・再計算せず、同じ採用・見学に新旧両方から決済を開始させないことを前提にしています。方針（確定済みとのことですが、本文を受け取っていません）との差分は、受領後に直します。

## 1. 既存の仕組み（変更しない）
| 既存 | 内容 | 本計画での扱い |
|---|---|---|
| `organization_contract_settings` | 会社ごとの契約状態・採用1名の固定額(`success_fee_amount`)・月額(`monthly_fee`) | 変更しない。旧方式の根拠として残す |
| `organization_subscriptions` + Stripe | 月額の定期課金 | 変更しない。新方式で月額無料になっても**自動で解約しない** |
| `hiring_success_fees`（pending_confirmation→confirmed→invoiced→paid/waived/cancelled） | 採用成立ごとの成功報酬。金額は運営が確定 | 変更・削除・再計算しない |
| `stripe_checkout_records`（purpose: success_fee 等） | 既存の決済 | 変更しない（新しい決済は別表 `admin_invoice_checkouts`） |
| scout credits | スカウトの有料枠 | 対象外（変更なし） |

## 1.5 調査で分かったこと（二重請求リスクの実在）
既存の `0039` は、採用が成立(`hired`)した時点で**旧の成功報酬の行（pending_confirmation）を自動で作る**トリガーを持つ。したがって、新方式に切り替えた会社でも、採用成立のたびに旧の行ができる。放置すると、運営が旧の行を確定し、さらに新しい採用料も請求する二重請求につながる。ローカルの検証では、新方式の会社で採用を成立させると旧の行が自動で作られ、検出SQLがそれを拾うことを確認した（2件検出）。
→ 対策は3章の1・3。旧の自動作成を止めるのは既存コードの変更になるため、**行は作られたままにして、新方式の会社では運営が既存の「免除(waived)」操作で閉じる運用＋検出SQL**を推奨案とする。トリガー自体の変更が必要かはレビューで決める。

## 2. 移行対象の分け方（会社単位・案件単位）
**会社ごとに「請求方式」を1つ持つ**（新しい小さな表 `organization_billing_regime(organization_id, regime in ('legacy','new'), effective_from, decided_by, decided_at)`。行が無い会社は `legacy`＝現状どおり）。切替は運営が会社ごとに明示的に行い、自動では行わない。

| 対象 | 扱い |
|---|---|
| 切替前に成立済み・請求済みの採用（`hiring_success_fees`が存在） | 旧方式のまま完結。新方式の請求行を作らない |
| 切替時点で `pending_confirmation / confirmed / invoiced` の旧成功報酬 | 旧方式で完結させる（運営が個別に確認）。新方式へ付け替える場合は、旧行を**運営が既存の「免除(waived)」操作で閉じた記録を残したうえで**、新しい行を作る。自動の付け替えはしない |
| 切替後に成立する採用 | 新方式（採用料: スタイリスト55万／アシスタント45万、税抜） |
| 見学（新規の概念） | 新方式のみ（実施確認1回につき5万・税抜） |
| 登録手数料 | 新方式の会社で、まだ登録手数料の行が無い場合のみ。既存契約会社への適用有無・時期は**未確定ケース**として個別確認 |
| 月額 | 新方式は当面無料。既存の月額サブスクは自動解約・返金しない。止める場合は運営が会社と合意した上でStripe側で個別に実施 |

## 3. 二重請求の防止（DBとアプリの二重）
1. **同じ採用に旧・新の両方を作らない**: 新方式の採用料の行を作る前に、その採用進行(`hiring_process_id`)に旧 `hiring_success_fees` が有効（cancelled/waived以外）で存在しないことを確認する。DB側は新しい請求行の追加時に検査するトリガーで拒否する（0062への追加案。既存の `hiring_success_fees` には触れない）。
2. **同じ案件×料金区分は1行**（0062で実装済み。`admin_invoice_lines` の部分一意index）。
3. **決済の入口を一つに**: 新しい決済開始は「新方式の会社」かつ「その請求が payment_pending」のときだけ。旧の決済開始（既存関数）は変更しないため、**新方式の会社に旧の成功報酬が `confirmed` で残らないよう、運営の確認画面で警告し、整合性チェックに載せる**（下の検出SQL）。旧関数を止める変更は既存コードの変更になるため、必要ならレビューで別に決める。
4. **同じ決済の同時進行は1つ**（0062で実装済み）／決済通知の重複処理は拒否（実装済み）。
5. 既存の請求を**削除・再計算するSQLは作らない**。切替で金額が変わる場合も、旧行は履歴として残す。

## 4. 重複リスクの検出SQL（読み取り専用・ローカルで検証）
`billing_overlap_check.sql` : 新方式の会社で旧成功報酬が未完結のもの／同じ採用に新旧両方の行があるもの／旧サブスクが有効なまま新方式になっている会社を一覧にする。運営画面の「整合性チェック」に接続する想定。

## 5. 決めていただきたいこと
- 既存契約会社への新料金の適用開始日（会社ごと／一斉）。
- 切替時点で未完結の旧成功報酬を、旧のまま完結させるか、免除して新方式で請求し直すか（会社ごと）。
- 登録済みの既存会社に登録手数料を請求するか。
- 既存の月額サブスクの扱い（自動では止めない前提で、止める手順の担当）。
