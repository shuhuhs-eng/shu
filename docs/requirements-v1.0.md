## 1. コンセプト

Beauty Reach は **AI × キャリアパートナー** によって、美容師とサロンの「採用」ではなく **定着まで支援する** 美容業界専門プラットフォームである。

- 診断・マッチングはAIが担う（スピードとスケール）
- 人が介在すべき局面（意思決定支援・条件交渉・入社後フォロー）は **キャリアパートナー** が担う
- ゴールは「採用成立」ではなく「定着」。定着データをAIにフィードバックし、診断・マッチング精度を継続的に改善する

## 3. Phase 1「オンボーディング」の定義（確定）

オンボーディングとは、**美容師・サロンがプロフィールや希望条件を登録する導入フロー**を指す。**「AIが最初の3店舗を提案する体験」はオンボーディングに含めず、Phase 5「マッチング」として分離する。**

### 3.1 美容師オンボーディングのステップ（今回実装）

```
① 基本情報 → ② キャリア → ③ 希望条件 → ④ 働き方・価値観 → ⑤ 保存 → ⑥ マイページ
```

具体的な画面一覧・入力項目・画面遷移は別紙 `docs/phase1-stylist-onboarding.md` に詳細を記載し、実装直前の最終確認として提示する。

### 3.2 サロンオンボーディングのステップ（今回は着手しない）

```
① 法人基本情報 → ② 店舗情報 → ③ 採用条件 → ④ 店舗カルチャー・教育方針 → ⑤ 保存 → ⑥ マイページ
```

## 4. マッチング方針（Phase 5・今回は着手しない）

```
① AIが最適な3店舗を提案する
② 美容師が「興味あり」を押した場合のみ、キャリアパートナーが介在する
③ 3店舗で決まらなければ、結果とフィードバックを反映して次の3店舗を提案する
④ ②③を繰り返す（サイクル）
```

- 1人の美容師に対する**同時提案は最大3店舗**
- **「3店舗で決まらない」の確定はAIの自動判定ではなく、キャリアパートナーが案件終了を判断する**（10.1節で確定）。終了後、AIが次の3店舗を再提案する

### 4.1 マッチングスコア算出に統合する要素（追記・Version 1.0 Final確定後）

将来の本格的なマッチング（Phase 5）は、単一の要素ではなく以下を統合して算出する設計とする。

- 8タイプ（美容師の front-facing 称号）
- 6才能スコア
- 希望条件
- 価値観
- 経験・キャリア
- 店舗カルチャー
- 教育方針
- 客層
- 店長・マネジメント傾向
- 在籍スタッフ構成
- 定着データ

**特に「在籍スタッフとの相性」は、将来のマッチング精度に影響する重要な要素として明記する。** 既存スタッフの傾向（例：どのタイプの美容師が多く在籍し、定着しているか）と、マッチング対象美容師のタイプ・価値観との相性を評価に組み込む想定。具体的な算出式・データ取得方法はPhase 5設計時に別途詳細化する。

現Phase（8タイプ導入）でマイページに表示する「相性の良いサロン傾向」は、上記の統合的なマッチングとは別物であり、**あくまで「その人の強みが活きやすい環境傾向」を示す参考情報**にとどめる（断定的な推薦表現は用いない）。

契約と請求は会社単位、AIマッチングは店舗単位とする。

## 6. キャリアパートナー（確定・今回は着手しない）

### 6.1 役割（8項目）

キャリア相談／希望条件整理／AI診断の解説／サロン提案／面接調整／条件調整／入社フォロー／定着フォロー

### 6.2 担当方式（確定）

- **固定担当制**。美容師が「興味あり」または「初回相談」を押した段階で担当を固定する
- 同じキャリアパートナーが、条件整理・3店舗提案・面接/見学調整・入社・定着確認まで一貫して伴走する
- **運営は途中で担当変更できる構造にする**（休職・退職・負荷超過等）
- **担当件数は30〜50名程度を想定する**
- 1人の美容師に対する同時提案は最大3店舗

### 6.3 連絡手段（確定）

**Phase 1時点ではLINE・電話・メールのみで運用する。アプリ内チャット機能は後日実装する。** 本書のAPI/DB設計では、アプリ内チャット用のテーブル（メッセージ本体等）は今回設計しない。連絡手段の記録（いつ・どの手段で連絡したかのログ）が必要になった場合は、キャリアパートナー評価制度（11章）のKPI算出に必要な範囲でのみ、`career_partner_engagements`の更新履歴から代替する。

## 8. 成果報酬（確定・今回は着手しない）

| イベント | 金額 | 備考 |
|---|---|---|
| 面接またはサロン見学を実際に実施 | ¥100,000 | 来なかった場合は請求しない |
| スタイリストが入社 | ¥300,000 | 面接・見学料金とは別請求 |
| アシスタントが入社 | ¥200,000 | 面接・見学料金とは別請求 |

面接・見学料金と入社料金は相互に充当しない。

### 8.1 実施判定〜請求確定のフロー（確定）

```
① キャリアパートナーが「見学（面接）実施」を登録
② 美容師が確認
③ サロンが確認
④ ①〜③がすべて揃った時点で請求対象として billing_events に計上
⑤ 運営が「請求対象確定」を承認
```

美容師・サロン双方の確認が揃わない限り、請求対象にはならない。

### 8.2 請求状態の管理（`billing_events`、確定）

```
発生前 → 請求対象確定 → 請求書発行済み → 入金済み
                                    ↘ 取り消し
                                    ↘ 返金
                                    ↘ 調整
```

**「取り消し」「返金」「調整」は明確に区別する**（同一のstatus値にまとめない）。目安：確定前の誤登録＝取り消し、入金後の金額誤り等の是正＝返金または調整（返金＝入金分を戻す、調整＝金額を修正して再確定する、という運用差を持たせる）。

## 10. 確定事項一覧（旧・要確認事項への回答）

10.1. **3店舗不成立の確定方法**：AIの自動判定ではなく、**キャリアパートナーが案件終了を判断する**。終了後、AIが次の3店舗を再提案する。

10.2. **Freeプランの範囲**：7.1節のとおり確定。

10.3. **法人ダッシュボードの内容**：7.3節のとおり確定。

10.4. **AI検索／高度分析の差分**：7.2節のとおり確定（ロジック共通、Premiumで詳細検索・AI優先推薦・高度分析を追加提供）。

10.5. **キャリアパートナーの担当規模**：雇用形態（社員／業務委託）は本書では未確定のまま運用判断とする。**担当件数は30〜50名程度**と確定。

10.6. **キャリアパートナーとの連絡手段**：6.3節のとおり、Phase 1はLINE・電話・メールのみ。アプリ内チャットは後日実装。

10.7. **MBTIの扱い**：**今回は実装しない。** Beauty Reach独自12タイプのみ実装する。将来MBTIを追加できるDB構造（`mbti_results`）だけ設計し、接続・生成ロジックには着手しない（12章）。

10.8. **AI解説文の生成タイミング**：**診断完了時に生成する。プロフィール更新時のみ再生成する**（その他のタイミングでは再生成しない）。

10.9. **店舗の「マッチング用スコア」の算出**：**AIが自動算出する。** 更新タイミングは「店舗情報更新」「定着データ更新」「アンケート更新」の3つ。

10.10. **面接・見学「実施」の確定基準**：8.1節のとおり確定（キャリアパートナー登録→美容師確認→サロン確認→請求対象計上→運営承認）。

10.11. **`billing_events`の状態区分**：8.2節のとおり、取り消し・返金・調整を明確に区別する。

10.12. **定着アンケートの要約結果の閲覧範囲**：**個人回答は非公開。AIが匿名化・要約した傾向データのみをマッチング精度向上に利用する**（社内学習データとしての利用に限定し、サロン側への個別共有は行わない）。

10.13. **既存`profiles.onboarding_step`の扱い**：**既存ユーザーは完了扱いとする。** 新しい4ステップの美容師オンボーディングウィザードは初回登録者のみが通過するフローとし、既存の完了済みユーザーは再オンボーディングを求めない。既存ユーザーが情報を変更したい場合は、**既存のプロフィール編集画面（`/profile/edit`）のみで対応可能**とし、編集画面自体はステップ化しない。

10.14. **12キャラクターの範囲**：イラスト・世界観・色・UI・AI解説・表現方法の**すべてを含む**、包括的なブランド表現の単位として扱う。

## 11. キャリアパートナー評価制度（追加要件・確定）

キャリアパートナーの業務品質を継続的に管理するため、以下のKPIを保持・算出できる設計にする。

- 面接実施率
- 入社率
- 6か月定着率
- 美容師満足度
- サロン満足度

算出は期間（例：月次）ごとのスナップショットとして保持し、担当件数（30〜50名程度）に対する実績を集計する設計とする（詳細テーブルは16.7節）。本評価制度の運用（誰が閲覧するか・人事評価への反映方法等）はキャリアパートナー機能実装時（Phase 6）に詳細設計する。今回はデータ構造の設計にとどめる。
